# Робот 1С — обратное подключение без публикации базы

Внешняя обработка, которая работает внутри сеанса 1С и сама опрашивает
«Периметр». Нужна там, где стандартный интерфейс OData недоступен:

- служба ИБ запрещает публиковать информационную базу на веб-сервере;
- используется **базовая версия** платформы (публикация не поддерживается);
- нет администратора, готового настраивать Apache/IIS.

Конфигурация при этом **не меняется**: внешняя обработка — просто файл,
как внешний отчёт. Снятия с поддержки не требуется.

## Как это работает

```
инструмент агента → RobotBackend → очередь заданий в шлюзе «Периметра»
                                        ↑ HTTP-опрос (long polling, 25 с)
                          обработка «Периметр: робот» в сеансе 1С
                                        ↓ результат
                    шлюз → RobotBackend → инструмент агента
```

Соединение всегда инициирует 1С. Входящих подключений к 1С нет вообще.

## Установка у заказчика

1. В `config/perimeter.yaml` включить шлюз:

   ```yaml
   robot:
     enabled: true
     host: "10.0.0.5"        # адрес «Периметра» в локальной сети заказчика
     port: 8092
     token: "<общий секрет>"  # обязателен, если host не loopback
   ```

   Публичные адреса запрещены — конфиг это проверяет (правило №0).

2. Собрать обработку из исходников (см. ниже) и передать администратору 1С.
3. Открыть обработку в 1С на «рабочем месте робота» под учётной записью с
   правами на чтение нужных справочников и документов.
4. Проверить связь: в журнале «Периметра» появится опрос от робота.

Рабочее место робота занимает одну клиентскую лицензию 1С и должно быть
запущено, пока агент нужен пользователям.

## Сборка .epf из исходников

Исходники: `robot_module.bsl` (текст модуля) и `src/ПериметрРобот.xml`
(описание объекта). Сборка — пакетная, без графического Конфигуратора:

```bash
./build_epf.sh /opt/1cv8/x86_64/8.3.27.1508/1cv8 /srv/1c/любая_база
```

Скрипт кладёт модуль в `Ext/ObjectModule.bsl`, вызывает
`/LoadExternalDataProcessorOrReportFromFiles` и печатает лог. База нужна
только как контекст запуска Конфигуратора — её данные не меняются.

Синтаксический контроль собранной обработки:

```bash
1cv8 DESIGNER /F <база> /CheckModules \
     -ExternalDataProcessorOrReport perimeter_robot.epf -ThinClient -Server \
     /Out check.log
```

Либо вручную: создать в Конфигураторе внешнюю обработку, вставить текст
модуля, сохранить как `perimeter_robot.epf`.

### Как запускать робота

Рядом с `perimeter_robot.epf` кладётся файл настроек `perimeter_robot.json`:

```json
{"autostart": true, "gateway": "http://10.0.0.5:8092", "token": "<токен>"}
```

Без этого файла (или с `autostart: false`) открытие обработки безопасно —
никакой цикл не стартует. С ним робот начинает опрос сразу при открытии:

- интерактивно: «Файл → Открыть» на рабочем месте робота;
- из командной строки: `1cv8 ENTERPRISE /F <база> /N <пользователь> /P <пароль>
  /Execute perimeter_robot.epf`.

**`/Execute` не запускает робота — проверено 2026-07-31.** На живой базе
(Windows Server 2022, платформа 8.3.27.1508, демобаза с данными) поставлен
чистый эксперимент: собрана обработка, тело модуля которой безусловно пишет
файл. При запуске `1cv8 ENTERPRISE /Execute проба.epf` файл не появился —
значит платформа тело модуля объекта не выполняет. Наш робот по той же
причине не сделал ни одного обращения к шлюзу.

Форма к обработке добавлена, и это **не помогло**: вторая проба — обработка
с формой, чей `ПриОткрытии` пишет файл, — при `/Execute` тоже ничего не
записала. Проверено и с отключённой «защитой от опасных действий»
(`DisableUnsafeActionProtection=true` в `conf.cfg`), и на базе без
пользователей.

**Вывод: из командной строки робот не запускается вообще.** Ему нужен
интерактивный сеанс 1С — «Файл → Открыть» на рабочем месте.

Это не обходной путь, а собственно модель работы продукта: робот живёт в
сеансе бухгалтера. На базовых версиях иначе и невозможно — там нет сервера
приложений, и регламентные задания выполняются только внутри клиентского
сеанса. Отсюда честная формулировка для заказчика: **робот работает, пока
открыта 1С**, а не круглосуточно.

Для крупных клиентов на ПРОФ-версиях остаётся вариант, который мы не
проверяли: внешнее соединение (COM, `V83.Application`) с отдельного сеанса —
там же, где базовым версиям оно запрещено.

### Форма и почему опрос не циклом

Раз робот живёт в сеансе человека, блокирующий цикл `Пока Истина` заморозил
бы бухгалтеру 1С. Поэтому форма опрашивает шлюз **обработчиком ожидания**
раз в 3 секунды и вызывает `ВыполнитьОдинЦикл()`, а ожидание на стороне
шлюза короткое (2 с вместо 25). Отзывчивость сеанса сохраняется, задержка
ответа растёт незначительно.

`ВыполнитьРаботу()` с блокирующим циклом оставлен для выделенного сеанса
робота — там замораживать нечего.

## Протокол заданий

Шлюз отдаёт задание JSON-объектом, робот возвращает результат с тем же `id`.

| Операция | Запрос | Ответ |
|---|---|---|
| `query` | `entity`, `conditions[]`, `select`, `order_by`, `top` | `rows[]` |
| `get` | `entity`, `ref_key`, `select` | `row` |
| `create_draft` | `entity`, `payload` | `row` (всегда `Posted=false`) |
| `metadata` | — | `entities: {сущность: [поля]}` |

Условие: `{"field": "Контрагент_Key", "op": "eq", "kind": "guid", "value": "..."}`;
операции — `eq`, `ge`, `le`, `contains`.

Логическая схема имён совпадает с OData (`Catalog_*`, `Document_*`, `Ref_Key`,
`Number`, `Date`, `Posted`, `<Реквизит>_Key`), поэтому маппинги и инструменты
агента одинаковы для обоих каналов — переключение канала не меняет ни промпт,
ни поведение агента.

## Guardrails

- Робот **не проводит документы**: `create_draft` записывает объект в режиме
  `РежимЗаписиДокумента.Запись` с `Проведен = Ложь`. Поле `Posted` из задания
  игнорируется намеренно.
- Создавать разрешено только документы; попытка создать элемент справочника
  завершается ошибкой.
- Всё, что робот выполнил, попадает в append-only журнал «Периметра» на нашей
  стороне, а на стороне 1С — в штатный журнал регистрации.

## Статус проверки

Что проверено:

- обработка **собирается** из этих исходников платформой 8.3.27 (`build_epf.sh`);
- модуль проходит **синтаксический контроль Конфигуратора**: `/CheckModules`
  отвечает «No syntax errors found!» (проверено 2026-07-29 на 8.3.27.1508);
- протокол обмена покрыт тестами целиком — с эмулятором робота
  (`tests/fakes/fake_robot.py`), повторяющим его поведение.

Что НЕ проверено: выполнение на базе с реальными данными. Синтаксический
контроль не проверяет обращения к метаданным (`Документы[Имя]`,
`Метаданные.Справочники.Найти`) — они разрешаются во время работы. Лицензионной
базы у проекта пока нет, а бесплатная учебная версия платформы не обслуживает
веб-доступ, поэтому полноценный стенд собрать не удалось.

**Перед первым внедрением обязательна проверка на тестовой копии базы
заказчика.** Ожидаемые места правок: имена реквизитов в маппингах
(`mappings/*.yaml`, помечены `TODO(verify)`) и типы ссылочных реквизитов в
`ЗначениеРеквизита`.
