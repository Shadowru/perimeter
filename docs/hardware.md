# Требования к железу и производительность

Обновлено: 2026-07-28.

## Минимальные требования (GLM-5.2 через colibri)

| Ресурс | Минимум | Рекомендовано |
|---|---|---|
| RAM | 16 ГБ (резидентная плотная часть ~9.9 ГБ int4) | 24+ ГБ; чем больше — тем больше кэш экспертов |
| Диск | ~380 ГБ свободно, NVMe | быстрый NVMe; второй SSD с зеркалом весов удваивает пропускную способность чтения |
| GPU | не требуется | опционально (CUDA/ROCm/Metal) — ярус VRAM для горячих экспертов |
| CPU | x86-64-v3 (AVX2) или ARMv8 | больше ядер → быстрее prefill |
| ОС | Linux, Windows 10/11, macOS | Linux |

## Цифры производительности

⚠️ **Происхождение цифр.** Таблица ниже — замеры **upstream colibri** (`vendor/colibri/docs/benchmarks.md`, v1.1.1). Наши собственные замеры на целевом железе — обязательный шаг перед публикацией маркетинговых материалов: запустить `python3 tools/bench_inference.py --model <веса>` и вписать результаты в раздел «Замеры Периметра» ниже.

| Железо | Декодирование | Примечание |
|---|---|---|
| 6× RTX 5090, 251 ГБ RAM | 5.8–6.8 tok/s, TTFT ~13 с | полная резидентность экспертов |
| EPYC 7443, 430 ГБ RAM | 1.0 tok/s | диск исключён (всё в RAM) |
| Apple M5 Max, 128 ГБ | 2.06 tok/s | Metal |
| Ryzen AI Max+ 395, 128 ГБ | 1.83 tok/s | устойчивый режим |
| DGX Spark GB10, 121 ГБ | 3.33 tok/s | тёплый кэш |
| Ryzen 9 9950X, 123 ГБ, PCIe5 NVMe | 0.28 tok/s | дисковый стриминг |
| i5-12600K, 32 ГБ | 0.08 tok/s | холодный, мало RAM |

**Главный фактор задержки — prefill (TTFT), не декодирование.** На дисковом стриминге prefill идёт единицы токенов/с: промпт в 15k токенов может обрабатываться десятки минут. Выводы для продукта:

- системный промпт и вывод инструментов — максимально компактные (бюджет: системный промпт ≤ 700 токенов);
- KV-persist включён (тёплый рестарт), контекст сессии переиспользуется;
- `CTX` поднимать осознанно: каждый KV-слот при CTX=4096 стоит сотни МБ RAM.

Качество int4-gs64: −8.2 п.п. к fp16 на сложных задачах (замер upstream на OLMoE A/B); групповые скейлы gs64 возвращают ~63% потерь по сравнению с per-row int4. Только контейнер gs64 + int8 MTP.

## Спекулятивное декодирование (MTP): недоступно в режиме сервера

Проверено 2026-07-29 и зафиксировано, чтобы не пробовать повторно. Мы конвертируем int8-голову MTP, но движок отключает спекуляцию, когда сервер работает в мультиплексном режиме (`SERVE_BATCH=1`): в логе прямо написано, что спекуляция «не ragged-safe» при нескольких KV-слотах. Попытка запустить сервер с одиночным слотом (`PERIMETER_SERVE_BATCH=0`, `--kv-slots 1`) приводит к отказу движка обрабатывать запросы: питон-шлюз вендореного сервера умеет только батчевый протокол. Изменение откачено.

Вывод: MTP доступен только в интерактивном `coli chat`. Чтобы получить его в продукте, нужна доработка серверного протокола движка — это уровень upstream, а не флаг конфигурации.

## Замеры Периметра (наши, измеренные)

Стенд: 8 vCPU (QEMU, AVX2), **31 ГБ RAM**, 1 ТБ NVMe (fio: 2,5 ГБ/с последовательное чтение), Ubuntu 26.04. Модель GLM-5.2 int4-gs64 + int8 MTP, 400 ГБ на диске, конвертирована из официального `zai-org/GLM-5.2-FP8`. Дата: 2026-07-29.

| Метрика | Значение |
|---|---|
| Загрузка модели до готовности | **26 с** |
| Пиковая память (сервер + движок) | **17,8 ГБ** |
| Декодирование | **0,07 ток/с** |
| TTFT, промпт 31 токен | **141,7 с** |
| TTFT, промпт 355 токенов | **686,4 с** |
| Ответ 32 токена, холодный / тёплый | 550 с / 471 с |

**Модель задержки** (из двух точек выше):

```
TTFT ≈ 90 с (постоянные издержки) + 1,68 с × число токенов промпта
```

Практический смысл: короткий вопрос без инструментов — примерно 2,5 минуты до первого слова. Запрос агента с четырьмя инструментами (~760 токенов после сжатия схем) — **около 23 минут только на prefill**, плюс генерация ответа по 14 секунд на токен.

### Почему так медленно: дело в RAM, а не в диске

Движок при старте сообщает расклад памяти:

```
[RAM_GB=23.3 auto] resident 11.4 GB + reserve 6.3 GB, experts 21.2 MB x 77 layers
                   -> cap lowered 8->3 (projected peak 22.6 GB)
```

Модель запрашивает **8 экспертов на слой на каждый токен**, а в кэш при 31 ГБ помещается только **3**. Значит почти каждый токен идёт на диск — отсюда и 0,07 ток/с, и медленный prefill. Диск здесь не виноват: 2,5 ГБ/с — приличная скорость, просто читать приходится слишком много.

Отсюда прямое следствие: **производительность определяется объёмом оперативной памяти**, и требования к железу надо формулировать в этих терминах.

### Требования к железу — по режимам использования

| Режим | RAM | Ожидание |
|---|---|---|
| Простые вопросы без инструментов | 32 ГБ | ~2,5 мин до первого слова, ответ на 100 слов — около получаса. Годится для проверки и демонстрации, не для работы |
| Агент с инструментами 1С | **128 ГБ** | по upstream-замерам на 128 ГБ — около 2 ток/с, то есть ответ за минуты. **Наш собственный замер на такой машине не делался** |
| Комфортная работа нескольких пользователей | 256+ ГБ или GPU-резидентность | upstream: 5,8–6,8 ток/с на 6× RTX 5090 |

Диск при любом раскладе: **NVMe, не менее 500 ГБ свободно** (модель занимает 400 ГБ). Сетевые тома и виртуализированные диски с урезанной полосой не подходят.

### Что осталось непроверенным

- Замеры на 128 ГБ RAM — своих нет, в таблице выше это отмечено. До них цифры для рекомендуемой конфигурации остаются заимствованными у upstream.
- Полный агентский сценарий против мок-1С на живой модели: **не дошёл до конца** на стенде (упёрся в 32 ГБ), см. STATUS.md.

Верификация движка при этом полная: teacher-forcing 32/32 совпадений с эталоном transformers, сквозной стриминг, качество ответов на русском по бухгалтерским вопросам — корректное.
