## 4. Интеграция с 1С:Предприятие 8.3 без доработок конфигурации

Целевые конфигурации: **Бухгалтерия предприятия 3.0 (БП 3.0), Управление торговлей 11 (УТ 11), Зарплата и управление персоналом 3.1 (ЗУП 3.1)**. Все три — управляемые формы на платформе 8.3, все поддерживают перечисленные ниже штатные механизмы.

### 4.1. Стандартный интерфейс OData — ✅ основной канал (выбран)

Платформа 8.3 (с 8.3.5) предоставляет автоматический REST-интерфейс поверх любой конфигурации.

**Что требуется на стороне клиента (без изменения конфигурации):**
1. Публикация информационной базы на веб-сервере (Apache/IIS) — штатная операция администратора («Публикация на веб-сервере» в конфигураторе, галочка «Публиковать стандартный интерфейс OData»).
2. Разрешение состава объектов OData. По умолчанию состав пуст; включается либо штатной обработкой/настройкой в самой конфигурации (в свежих БП 3.0 / УТ 11 есть настройка «Настройка доступа к интерфейсу OData»), либо однократным вызовом `УстановитьСоставСтандартногоИнтерфейсаOData()` из внешней обработки. Это **администрирование, не доработка конфигурации**.

**Возможности, важные для нас:**
- URL: `http(s)://<host>/<base>/odata/standard.odata/` + имя сущности; JSON через `$format=json` или заголовок `Accept: application/json`.
- Имена сущностей строятся из метаданных: `Catalog_<Имя>`, `Document_<Имя>`, `InformationRegister_<Имя>`, `AccumulationRegister_<Имя>`, и т.д. Имена — **русские идентификаторы метаданных** (URL-кодируются).
- Выборка: `$filter`, `$select`, `$top`, `$skip`, `$orderby`, `$expand`, `$count`. Пагинация — `$top`/`$skip` (серверного `@odata.nextLink` в 1С нет — листаем сами).
- Аутентификация: HTTP Basic (пользователь ИБ) — пароль храним в keyring/env, не в конфиге.
- Запись: `POST` (создание), `PATCH` (изменение), `DELETE`(пометка удаления — на деле через `DeletionMark`). Проведение/отмена проведения документа — операции `Post`/`Unpost` (`POST .../Document_X(guid'...')/Post()?PostingModeOperational=false`). **В нашем продукте `Post` агенту запрещён** (только черновики: `POST` с `Posted=false`).

**Ожидаемые имена объектов (стандартные метаданные; TODO: верифицировать на живой базе перед релизом, имена вынести в конфиг, не хардкодить):**
- БП 3.0 / УТ 11: `Catalog_Контрагенты`, `Catalog_Номенклатура`, `Document_РеализацияТоваровУслуг`, `Document_ПоступлениеТоваровУслуг`, `Document_СчетНаОплатуПокупателю` (в УТ 11 — `Document_ЗаказКлиента` и др. — состав отличается!).
- Ключевые поля документа: `Ref_Key` (GUID), `Number`, `Date`, `Posted`, `DeletionMark`, `Контрагент_Key`. — TODO: подтвердить состав по `$metadata` конкретной базы; клиент должен уметь читать `$metadata`.
- Взаиморасчёты (сверка): `AccumulationRegister_РасчетыСПокупателями` (БП 3.0) / регистры взаиморасчётов УТ. — TODO: имена регистров различаются между конфигурациями и версиями, обязательно конфигурируемо.

**Ограничения OData:** нет виртуальных таблиц регистров (остатки/обороты) напрямую — остатки считаем сами по движениям либо читаем `AccountingRegister_Хозрасчетный_RecordType` с фильтрами (тяжело); для отчётов типа ОСВ это компромисс, фиксируем в дизайне `ledger_report`.

### 4.2. HTTP-сервисы — ⚠️ требуют доработки (или расширения)

HTTP-сервисы — объекты конфигурации; в типовых БП/УТ/ЗУП «под нас» их нет. Добавление = доработка. **Но**: их можно поставлять как **расширение конфигурации (.cfe)** — ставится без снятия с поддержки, переживает обновления типовой. Это план Б для операций, которые неудобны через OData (например, серверный расчёт остатков). В MVP не используем.

### 4.3. COM-соединение (V83.COMConnector) — ❌ не для MVP

Только Windows, требует установленной платформы 1С на машине «Периметра», регистрации comcntr.dll, лицензии на сеанс. Мощно (полный доступ к объектной модели), но хрупко и непереносимо. Оставляем как потенциальный канал для Windows-инсталляций в будущем.

### 4.4. Выгрузки (файловый обмен) — 🔄 резервный канал

Штатные механизмы: «Универсальный обмен данными XML», выгрузка через обработки, планы обмена/EnterpriseData. Плюсы: работает даже когда нет веб-публикации, максимальный «воздушный зазор». Минусы: не realtime, требует настройки регламентных заданий. Держим в уме для клиентов, у которых ИБ-политика запрещает даже внутренний HTTP к 1С.

### 4.5. Решение

**MVP: только OData** (чтение + создание непроведённых черновиков). Все имена сущностей/полей — в конфигурационном слое (`bridge-1c` mapping-файлы per-конфигурация: `bp30.yaml`, `ut11.yaml`, `zup31.yaml`), клиент валидирует их против `$metadata` при первом подключении. Хосты 1С — только из `config/perimeter.yaml`.
