## 2. Архитектура openworker (andrewyng/openworker, MIT, ~34k строк Python)

**Ядро** — пакет `coworker/`:
- `engine.py :: TurnEngine` — агентный цикл: стрим модели → события → батч tool-вызовов → результат в историю; ограничение итераций; прерывание/steering посреди хода; ретраи. Провайдерский вызов блокирующий, обёрнут в executor.
- История — `list[dict]` в **каноническом OpenAI chat-формате** (`role/content/tool_calls/tool_call_id`); единственная точка выдачи истории провайдеру — `_outbound_messages()` (engine.py:878).
- **Провайдеры** — `providers/base.py :: ProviderClient` (`complete()`, `stream()`, `capabilities()`); роутер по префиксу модели (`ollama:...`). Есть готовый localhost-путь: `OpenAIProvider(base_url=...)`, дескриптор ollama (`http://localhost:11434/v1`).
- **Инструменты** — `tools/registry.py :: ToolSpec{name, schema(OpenAI-формат), func, metadata}`; metadata (`risk_level`, `requires_approval`) управляет параллельностью и `PermissionEngine`. Чистая точка расширения: callable + `__coworker_schema__`.
- **Skills** — папка со `SKILL.md` (frontmatter + markdown), прогрессивная подгрузка: в промпт попадают только `name: description`, тело — по требованию инструментом `load_skill`. **Personas** — YAML-frontmatter + markdown = системный промпт.
- Ценное для локальной модели: `openai_provider.py :: _salvage_tool_calls_from_text()` — восстановление tool-вызовов, пришедших текстом (`<tool_call>{...}</tool_call>`, Hermes-XML и т.п.) с валидацией по схемам.

**Критичные находки:**
- ⚠️ **Компактизации/суммаризации истории НЕТ вообще** — история растёт до ошибки провайдера. Для локальной модели (CTX 4096 у colibri по умолчанию) строим сами; шов — `_outbound_messages()`.
- Для air-gap пришлось бы вырезать: `cloud.py` (телеметрия, Auth0), `connectors/` (~12k строк SaaS-интеграций + WebSocket-relay на AWS), `web/` (DuckDuckGo/Tavily), MCP-OAuth, GUI auto-update, загрузку whisper-модели в `stt/`. Плюс тащить зависимости: openai SDK, aisuite (git-зависимость!), pydantic (компилируемое Rust-ядро), fastapi/uvicorn.

### Решение по core/

**Не форкаем openworker целиком** — вендорить pydantic/openai-SDK/aisuite ради ядра, из которого вырезается половина, противоречит правилу №0 и раздувает аудит. Делаем **компактную адаптацию архитектуры** («в духе openworker», как и сформулировано в задаче) на чистом stdlib:
переносим паттерны: TurnEngine-цикл, канонич. OpenAI-история, ToolRegistry с OpenAI-схемами и risk-metadata, единый шов outbound_messages (+ наша компактизация), salvage текстовых tool-вызовов, skills-формат SKILL.md. Лицензионно чисто (MIT позволяет и форк, и заимствование), фиксируем происхождение идей здесь.

## 3. Архитектура colibri (JustVugg/colibri v1.1.1, Apache-2.0)

**Движок** — один C-файл `c/colibri.c` (~6.7k строк) + заголовки; ноль зависимостей, BLAS не нужен, GPU опционален (CUDA/HIP/Metal — opt-in при сборке). Сборка: `cd c && make portable` (переносимый бинарь, x86-64-v3), **никаких загрузок при сборке**.

**Идея**: GLM-5.2 744B MoE активирует ~40B параметров/токен. Плотная часть (~9.9 ГБ int4) резидентна в RAM; 19 456 экспертов (~370 ГБ int4) стримятся с диска с LRU-кэшем, обучаемым hot-store и опциональным VRAM-ярусом. Плейсмент влияет только на скорость, не на качество.

**Сервер** — `c/openai_server.py` (~1.7k строк, **только stdlib**): `/v1/chat/completions` (+legacy `/v1/completions`, + Anthropic `/v1/messages`), SSE-стриминг с keepalive, привязка к 127.0.0.1 по умолчанию, отказ слушать не-loopback без API-ключа (fail-closed), защита от DNS-rebinding, очередь с 429. Связь с движком — subprocess по stdin/stdout (протокол в `docs/serve_protocol.md`). Это ровно наш Этап 3 — **сервер уже есть**, нам остаётся обёртка/конфиг/надзор.

**Формат чата GLM-5.2**: `[gMASK]<sop><|system|>…<|user|>…<|assistant|>`; tool-вызовы — текстовые маркеры `<tool_call>{name}<arg_key>…</tool_call>`, результат — `<|observation|><tool_response>`. Сервер парсит и отдаёт их в OpenAI-виде. ⚠️ `response_format`/грамматика — **только ускоритель декодирования, НЕ ограничение выборки**: валидность JSON гарантируем своим слоем с ретраем. ⚠️ Не поддержаны: `stop`, `logprobs`, penalties, `seed`, `n>1`, картинки. CTX по умолчанию 4096 (KV-кэш; модель умеет 131072 — поднимаем CTX за счёт RAM).

**Измеренные цифры производительности** (docs/benchmarks.md):

| Железо | tok/s |
|---|---|
| 6× RTX 5090, 251 ГБ RAM (полная резидентность) | 5.8–6.8, TTFT ~13 с |
| EPYC 7443, 430 ГБ RAM | 1.0 |
| Apple M5 Max 128 ГБ (Metal) | 2.06 |
| Ryzen AI Max+ 395, 128 ГБ | 1.83 |
| Ryzen 9 9950X, 123 ГБ, PCIe5 NVMe | 0.28 |
| i5-12600K, 32 ГБ | 0.08 |

Минимум: ~16 ГБ RAM + ~380 ГБ NVMe. **Главный риск — prefill (TTFT)**: на дисковом стриминге длинный промпт обрабатывается минутами. Следствия для продукта: системный промпт и вывод инструментов — максимально компактные; KV-persist / warm-restart включить; замеры Этапа 3 обязательно включают TTFT при нашем реальном промпте.

**Воздушный зазор**: grep по всему C-коду — ни одного сетевого символа; телеметрии/auto-update нет; сеть только в setup-скриптах загрузки весов (`download_fp8.py` и `tools/download_*` — в вендоринг не включаем или помечаем setup-only). Каталог модели пишется в рантайме (`.coli_usage`, `.coli_kv`) — учесть права на запись.

**Веса**: официальный источник `zai-org/GLM-5.2-FP8` (MIT, подтверждено 2026-07-28 через HF API) → конвертация `coli convert` в int4-gs64 (~372 ГБ) у нас — чистая цепочка происхождения. Community-реаплоуд `mastouri/...` не используем в продукте.

**CI без большой модели**: `make check` (юнит-тесты C + stdlib-тесты сервера с FakeEngine, ноль загрузок); генератор крошечной GLM-MoE-фикстуры `c/tools/make_glm_bench_model.py` — вариант для e2e в CI. Отдельный движок `olmoe` для квант-исследований нам не нужен.

## 4. Интеграция с 1С:Предприятие 8.3 без доработок конфигурации

Целевые конфигурации: **Бухгалтерия предприятия 3.0 (БП 3.0), Управление торговлей 11 (УТ 11), Зарплата и управление персоналом 3.1 (ЗУП 3.1)**. Все три — управляемые формы на платформе 8.3, все поддерживают перечисленные ниже штатные механизмы.

### 4.1. Стандартный интерфейс OData — ✅ основной канал (выбран)

Платформа 8.3 (с 8.3.5) предоставляет автоматический REST-интерфейс поверх любой конфигурации.

**Что требуется на стороне клиента (без изменения конфигурации):**
1. Публикация информационной базы на веб-сервере (Apache/IIS) — штатная операция администратора («Публикация на веб-сервере» в конфигураторе, галочка «Публиковать стандартный интерфейс OData»).
2. Разрешение состава объектов OData. По умолчанию состав пуст; включается либо штатной обработкой/настройкой в самой конфигурации (в свежих БП 3.0 / УТ 11 есть настройка «Настройка доступа к интерфейсу OData»), либо однократным вызовом `УстановитьСоставСтандартногоИнтерфейсаOData()` из внешней обработки. Это **администрирование, не доработка конфигурации**.

**Возможности, важные для нас:**
- URL: `http(s)://<host>/<base>/odata/standard.odata/` + имя сущности; JSON через `$format=json` или заголовок `Accept: application/json`.
- Имена сущностей строятся из метаданных: `Catalog_<Имя>`, `Document_<Имя>`, `InformationRegister_<Имя>`, `AccumulationRegister_<Имя>`, и т.д. Имена — **русские идентификаторы метаданных** (URL-кодируются).
- Выборка: `$filter`, `$select`, `$top`, `$skip`, `$orderby`, `$expand`, `$count`. Пагинация — `$top`/`$skip` (серверного `@odata.nextLink` в 1С нет — листаем сами).
- Аутентификация: HTTP Basic (пользователь ИБ) — пароль храним в keyring/env, не в конфиге.
- Запись: `POST` (создание), `PATCH` (изменение), `DELETE`(пометка удаления — на деле через `DeletionMark`). Проведение/отмена проведения документа — операции `Post`/`Unpost` (`POST .../Document_X(guid'...')/Post()?PostingModeOperational=false`). **В нашем продукте `Post` агенту запрещён** (только черновики: `POST` с `Posted=false`).

**Ожидаемые имена объектов (стандартные метаданные; TODO: верифицировать на живой базе перед релизом, имена вынести в конфиг, не хардкодить):**
- БП 3.0 / УТ 11: `Catalog_Контрагенты`, `Catalog_Номенклатура`, `Document_РеализацияТоваровУслуг`, `Document_ПоступлениеТоваровУслуг`, `Document_СчетНаОплатуПокупателю` (в УТ 11 — `Document_ЗаказКлиента` и др. — состав отличается!).
- Ключевые поля документа: `Ref_Key` (GUID), `Number`, `Date`, `Posted`, `DeletionMark`, `Контрагент_Key`. — TODO: подтвердить состав по `$metadata` конкретной базы; клиент должен уметь читать `$metadata`.
- Взаиморасчёты (сверка): `AccumulationRegister_РасчетыСПокупателями` (БП 3.0) / регистры взаиморасчётов УТ. — TODO: имена регистров различаются между конфигурациями и версиями, обязательно конфигурируемо.

**Ограничения OData:** нет виртуальных таблиц регистров (остатки/обороты) напрямую — остатки считаем сами по движениям либо читаем `AccountingRegister_Хозрасчетный_RecordType` с фильтрами (тяжело); для отчётов типа ОСВ это компромисс, фиксируем в дизайне `ledger_report`.

### 4.2. HTTP-сервисы — ⚠️ требуют доработки (или расширения)

HTTP-сервисы — объекты конфигурации; в типовых БП/УТ/ЗУП «под нас» их нет. Добавление = доработка. **Но**: их можно поставлять как **расширение конфигурации (.cfe)** — ставится без снятия с поддержки, переживает обновления типовой. Это план Б для операций, которые неудобны через OData (например, серверный расчёт остатков). В MVP не используем.

### 4.3. COM-соединение (V83.COMConnector) — ❌ не для MVP

Только Windows, требует установленной платформы 1С на машине «Периметра», регистрации comcntr.dll, лицензии на сеанс. Мощно (полный доступ к объектной модели), но хрупко и непереносимо. Оставляем как потенциальный канал для Windows-инсталляций в будущем.

### 4.4. Выгрузки (файловый обмен) — 🔄 резервный канал

Штатные механизмы: «Универсальный обмен данными XML», выгрузка через обработки, планы обмена/EnterpriseData. Плюсы: работает даже когда нет веб-публикации, максимальный «воздушный зазор». Минусы: не realtime, требует настройки регламентных заданий. Держим в уме для клиентов, у которых ИБ-политика запрещает даже внутренний HTTP к 1С.

### 4.5. Решение

**MVP: только OData** (чтение + создание непроведённых черновиков). Все имена сущностей/полей — в конфигурационном слое (`bridge-1c` mapping-файлы per-конфигурация: `bp30.yaml`, `ut11.yaml`, `zup31.yaml`), клиент валидирует их против `$metadata` при первом подключении. Хосты 1С — только из `config/perimeter.yaml`.

## Открытый вопрос: базовые версии 1С (2026-07-31)

Мы утверждали в README и на лендинге, что обратное подключение «работает и
на базовой версии». Проверка показала, что утверждение непроверенное, и
формулировки сняты до подтверждения на живой базе.

Что известно по источникам:

- на базовых версиях **публикация ИБ невозможна** — OData отпадает, это
  подтверждено и не оспаривается;
- базовые версии **не допускают внешнее соединение** (COM) — этот канал
  тоже отпадает;
- **интерактивное открытие** внешних отчётов и обработок на базовой
  платформе ограничено;
- штатный путь для внешней обработки — регистрация в справочнике
  «Дополнительные отчёты и обработки» (механизм БСП, есть в типовой
  Бухгалтерии 3.0).

Отсюда рабочая гипотеза: робот на базовой версии запускается **не** через
«Файл → Открыть», а через регистрацию в «Дополнительных отчётах и
обработках». Гипотезу нужно проверить на живой базовой базе.

Второй, не менее важный вопрос: **как робот живёт долго**. На базовой версии
нет сервера приложений, поэтому регламентные задания выполняются только
внутри открытого сеанса клиента. Значит, робот работает, пока у пользователя
открыта 1С. Для бухгалтера это может быть приемлемо (1С открыта весь день),
но обещать «круглосуточно» нельзя.

Пока не проверено — в маркетинговых материалах базовые версии не упоминаем.

Источники (вторичные, требуют подтверждения на живой базе):
https://infostart.ru/1c/articles/98417/ ,
https://gendalf.ru/news/manager/khvatit-li-vam-bazovoy-versii-1sbukhgalt/

## Запуск робота: `/Execute` не работает (проверено 2026-07-31)

Стенд: Windows Server 2022, учебная платформа 8.3.27.1508, демобаза с данными,
всё управлялось по SSH без графики.

Что подтвердилось:

- платформа ставится тихой установкой, база разворачивается из выгрузки,
  Конфигуратор работает в пакетном режиме — автоматизация возможна целиком;
- `perimeter_robot.epf` **собирается из исходников** на живой платформе
  (`/LoadExternalDataProcessorOrReportFromFiles`) и проходит синтаксический
  контроль: «Синтаксических ошибок не обнаружено!».

Что опровергнуто:

- **`1cv8 ENTERPRISE /Execute <обработка.epf>` не выполняет тело модуля
  объекта.** Поставлен чистый эксперимент: собрана обработка, тело модуля
  которой безусловно создаёт файл. После `/Execute` файла нет. Робот по той
  же причине не сделал ни одного обращения к шлюзу.

Проверено дополнительно (31.07, после первой записи):

- гипотеза «мешает защита от опасных действий» **не подтвердилась**: с
  `DisableUnsafeActionProtection=true` в `conf.cfg` результат тот же;
- гипотеза «нужна форма» **тоже не подтвердилась**: обработка с формой, чей
  `ПриОткрытии` пишет файл, при `/Execute` не записала ничего.

Значит дело не в устройстве обработки, а в том, что командная строка не
поднимает интерактивный сеанс.

Практические следствия:

1. Робот запускается **только интерактивным открытием** обработки в сеансе
   1С. Форма ему всё равно нужна — но не ради `/Execute`, а чтобы опрашивать
   шлюз обработчиком ожидания, не морозя сеанс бухгалтера.
2. Это согласуется с ограничением базовых версий: там нет сервера приложений,
   регламентные задания живут только в сеансе клиента. То есть «робот внутри
   открытого сеанса» — не костыль, а единственно возможная модель для
   массового сегмента.
3. Обещать «круглосуточную работу без участия человека» нельзя. Честная
   формулировка: робот работает, пока у пользователя открыта 1С.

Мелочи, стоившие времени и записанные, чтобы не повторять:

- `Invoke-WebRequest` молча отдаёт пустой файл на больших загрузках — нужен
  `curl.exe`;
- `.ps1` с кириллицей читается как ANSI, если сохранён без BOM;
- 1С без `/DisableStartupDialogs` **зависает** на диалоге аутентификации, а не
  падает: 44 минуты «работы» при 2 секундах процессорного времени;
- процессы, запущенные из SSH-сессии Windows, гибнут вместе с ней;
- `ssh-keygen -N ""` в PowerShell теряет пустую строку, и ключ получает
  парольную фразу `-q`.

## Робот выполнен на живой базе (2026-07-31)

Первое в истории проекта выполнение `robot_module.bsl` на настоящей 1С.
Обработка открыта интерактивно в сеансе, прочитала `perimeter_robot.json`,
опрашивала шлюз каждые 3 секунды, получила задание `metadata`, выполнила его
на «Бухгалтерии предприятия» 3.0.111 и вернула **798 объектов метаданных**
(1 МБ JSON).

Что это дало помимо самого факта:

- **Робот поймал ошибку в моей проверке маппинга.** Разбирая XML-выгрузку
  конфигурации, я собирал реквизиты рекурсивно и смешал реквизиты шапки с
  колонками табличных частей. Из-за этого `СуммаНДС` числился реквизитом
  документа. Робот перечисляет `ОбъектМетаданных.Реквизиты` — только шапку —
  и показал, что такого реквизита нет. Проверка независимым путём окупилась
  сразу.
- **`/CheckModules` не заменяет запуск.** Собранная обработка проходила
  синтаксический контроль, но при открытии упала: `Новый Файл(...).Существует()`
  — 1С не разрешает вызывать метод у результата `Новый`. Пакетный контроль
  этого не увидел.
- **Форме нужен реквизит «Объект».** Без него обращение к методам обработки
  падает с «Недопустимое значение параметра (параметр номер 1)».

Ограничение прежнее: это учебная платформа и учебная редакция конфигурации.
Имена метаданных совпадают с боевыми, но проверку имён при подключении
клиент выполняет всё равно.
