# Юниты systemd

Разложены по назначению; пути — `/opt/perimeter`, поправьте под себя.

    sudo cp tools/systemd/perimeter-live.service /etc/systemd/system/
    sudo systemctl daemon-reload && sudo systemctl enable --now perimeter-live

| Юнит | Зачем |
|---|---|
| `perimeter-live.service` | рабочий режим: модель, агент, веб-интерфейс, шлюз робота |
| `perimeter-tunnel.service` | канал до машины с 1С, если она отдельная (см. ниже) |
| `perimeter-demo.service` | демонстрация на вымышленных данных мок-1С |
| `perimeter-expose.service` | ВРЕМЕННЫЙ внешний доступ к демо с паролем — только на показ |

## Про туннель

Шлюз робота слушает loopback и наружу не открывается — это правило №0.
Если 1С стоит на другой машине, обратный проброс делает шлюз доступным как
`127.0.0.1` уже на ней: оба конца остаются на loopback, а между машинами
идёт шифрованный канал. У заказчика ту же роль обычно играет VPN между
офисом и сервером.

Проверено 2026-07-31 на связке Linux («Периметр») + Windows Server (1С):
робот в сеансе 1С опрашивал шлюз через этот проброс и отвечал на задания.

## Про perimeter-expose

Веб-интерфейс «Периметра» аутентификации не имеет и слушает loopback — так
задумано: доступ к нему равен доступу к данным 1С. Этот юнит выставляет
демо наружу с паролем **только на время показа**. В рабочей установке его
не включают: для удалённого доступа есть SSH-туннель или обратный прокси
заказчика с его же контролем доступа.
